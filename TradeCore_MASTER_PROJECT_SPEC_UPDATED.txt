1. PRODUCT IDENTITY
====================================================================

PROJECT NAME
------------
TradeCore

FULL WORKING NAME
-----------------
TradeCore — Trading Order Management & Portfolio Simulation Platform

PRODUCT TYPE
------------
A retail trading-learning / virtual trading platform with a realistic order-management
and portfolio-processing backend.

CORE IDEA
---------
TradeCore uses real market information for a limited universe of real Indian companies,
while all money, orders, executions, holdings, portfolio state and financial activity
inside TradeCore are virtual and simulated.

REAL WORLD INPUT
----------------
- Real company/instrument information
- Real market prices and market updates when the current market-data provider is available
- Real market-session concepts and Indian-market trading behavior

INTERNAL SIMULATION
-------------------
- Simulated money, including the initial virtual capital and all account balances
- Simulated orders; orders are internal learning actions and are never sent to an exchange
- Simulated execution, including fills, partial fills, and execution prices selected by the simulator
- Simulated portfolio/positions and valuation based on real market data
- Simulated realized and unrealized P&L based on simulated executions and portfolio state
- User accounts
- Virtual trading accounts
- Holdings/positions
- Ledger
- Risk rules
- Notifications
- Audit trail
- Intraday square-off

TradeCore is NOT a real brokerage and MUST NOT place real trades.

6. REALTIME MARKET-DATA EXPERIENCE
====================================================================

The website must feel live.

EXPECTED USER EXPERIENCE
------------------------
A user opens the application and sees the current market state.
While the market is open, prices can change without refreshing the page.
Watchlists, market tables, instrument pages and relevant portfolio information should react
to live updates.

PREFERRED DATA FLOW
-------------------
NSE MCP
    -> provider adapter
    -> validation/normalization
    -> internal market event
    -> update latest market state
    -> Redis/current-state cache
    -> publish realtime event
    -> WebSocket
    -> connected Next.js clients

Do NOT make every browser call the external provider directly.
The frontend talks to TradeCore.

DO NOT USE SLOW POLLING FOR LIVE PRICES
---------------------------------------
Do not build a design where every client polls prices every second.
Use the provider's stream/update mechanism where available, then distribute relevant updates
from the backend over WebSocket.

If the actual provider cannot deliver true streaming for some field, degrade gracefully and
use the smallest sensible refresh interval for that specific field. Do not fake realtime data.

8. MARKET SESSIONS
====================================================================

TradeCore must understand Indian equity-market sessions rather than assuming the market is
always open.

At minimum model:
- PRE_OPEN
- OPEN
- SQUARE_OFF_WINDOW
- CLOSED
- HOLIDAY

The live session calendar, trading day rules and holiday rules must be configurable and should

Current standard NSE equity-market behavior to model includes a 9:00–9:15 pre-open period and
a 9:15–3:30 regular session. Treat the actual exchange calendar/provider behavior as the source
for operational configuration rather than scattering hard-coded times through the code.

Market hours and data availability are separate concepts.

10. MARKET-DATA STORAGE OPTIMIZATION
====================================================================

Storage is limited and the application must remain fast.

CRITICAL RULE:
Do NOT permanently store every raw market tick forever.

HOT/CURRENT DATA
----------------
Use Redis and/or optimized current-state memory for:
- latest quote
- latest price
- latest bid/ask
- current market status
- freshness metadata
- high-frequency read data

PERMANENT DATA
--------------
PostgreSQL should retain data that is important for:
- financial correctness
- chart/history requirements
- business auditability
- reconstruction of user activity
- executions
- orders
- positions
- ledger
- sessions
- important system events

HISTORICAL MARKET DATA
----------------------
Prefer candles/aggregated historical data for long-term chart storage instead of keeping all
raw ticks.

FINANCIAL EXECUTION DATA
------------------------
Whenever a simulated execution occurs, persist the market reference/context that was actually
used to make the execution decision, including execution price and relevant timestamp/quote
information. This is required for reproducibility and auditability.

RETENTION / RETIREMENT
----------------------
Temporary high-frequency data should expire automatically.
Historical data should use a deliberate retention policy.
Use database indexes, partitioning or other optimizations only where justified by actual query
patterns and data volume.
Do not introduce complicated data infrastructure before it is needed.

11. WEB PERFORMANCE REQUIREMENTS
====================================================================

Performance is a first-class product requirement.

The website must respond quickly and should not feel slow because of unnecessary client-side
JavaScript or repeated API calls.

NEXT.JS PERFORMANCE RULES
-------------------------
- Prefer server components for non-interactive content.
- Keep client components small and focused.
- Do not make the entire application a client component.
- Lazy-load heavy charting/analytics code.
- Avoid loading large datasets when only a small visible page is needed.
- Use pagination/infinite loading for long histories where appropriate.
- Use table virtualization if a table can become large.
- Cache stable metadata such as instrument master data.
- Do not poll every market widget independently.
- Maintain a single efficient realtime subscription strategy.
- Batch/merge UI updates when many symbols update together.
- Do not cause full-page rerenders for a single price change.
- Use loading placeholders only where they improve perception; do not animate everything.
- Avoid excessive animations, gradients, shadows, and visual effects.
- Keep navigation responsive and predictable.

BACKEND PERFORMANCE RULES
-------------------------
- Redis for hot market state and high-read data where justified.
- PostgreSQL for transactional truth.
- Proper indexes for frequent queries.
- Avoid N+1 query patterns.
- Paginate order/trade/audit history.
- Use DTO/projection queries when full entities are not required.
- Keep transaction boundaries focused.
- Avoid holding database transactions open while waiting for external network calls.
- Do not perform unnecessary synchronous work in request threads.
- Process market updates efficiently.
- Avoid writing every tick directly to PostgreSQL.
- Avoid duplicate WebSocket messages to a client.
- Rate-limit sensitive APIs where appropriate.
- Monitor slow queries and meaningful application metrics.

REALTIME PERFORMANCE TARGET
---------------------------
The target is fast propagation, not a fake fixed number.
When a provider update arrives and is valid, distribute the internal update to subscribed
clients with minimal processing overhead.

The system should remain usable even if many users are watching the same 80 instruments.

19. ORDER STATE MACHINE
====================================================================

Orders must follow explicit valid state transitions.

PRIMARY FLOW
------------
CREATED
  -> VALIDATING
  -> ACCEPTED
  -> PENDING
  -> PARTIALLY_FILLED
  -> FILLED

REJECTION FLOW
--------------
CREATED
  -> VALIDATING
  -> REJECTED

CANCELLATION FLOW
-----------------
PENDING
  -> CANCEL_REQUESTED
  -> CANCELLED

FAILURE FLOW
------------
PENDING
  -> FAILED

Invalid transitions must be rejected.
Examples:
- FILLED -> PENDING
- CANCELLED -> FILLED
- REJECTED -> FILLED

The order status must not be freely overwritten by arbitrary service code.

Order event/history should preserve significant status changes and reasons.

====================================================================
21. DELIVERY TRADING
====================================================================

DELIVERY is intended for holdings that can remain after the trading session.

DELIVERY BUY
------------
Example:
BUY 10 TCS DELIVERY

The user pays for the simulated purchase through the virtual account and receives a delivery
position that remains after the market closes.

DELIVERY SELL
-------------
The system verifies the user has sufficient sellable quantity.
On successful execution, the position quantity is reduced and simulated proceeds are credited.

Delivery positions are not automatically squared off at the end of the trading session.


====================================================================
22. INTRADAY TRADING
====================================================================

INTRADAY positions are intended to be closed during the same trading session.

The first implementation should keep the financial model understandable and safe.
Do not introduce real-money leverage or a complicated margin engine just to look advanced.

If short selling is not fully supported by the chosen risk/margin design, keep the initial model
long-only for intraday and require an existing sellable intraday quantity for SELL.
Document this limitation rather than creating a fake margin system.

INTRADAY LIFECYCLE
------------------
Trading session starts
    -> intraday order flow
    -> intraday positions
    -> user closes positions normally
    -> square-off window begins
    -> remaining intraday positions identified
    -> automatic square-off processing
    -> simulated execution
    -> positions closed
    -> intraday P&L finalized

The square-off rule should be configurable and based on the configured market session.
The initial simulation can use a 3:20 PM IST square-off trigger to mirror common retail-broker
behavior, but the time must not be hard-coded into many unrelated components.

23. BUY PROCESS
====================================================================

PROCESS

14. Update ledger.
15. Update available/reserved balance safely.
16. Update position.
17. Recalculate P&L.
18. Emit order/execution/portfolio events.
19. Notify user.
20. Create audit record.

====================================================================
25. FUNDS AND QUANTITY RESERVATION
====================================================================

Reservation is required to prevent two simultaneous orders from spending/using the same
virtual resource.

BUY RESERVATION
---------------
If an order needs ₹20,000, reserve that amount before allowing another concurrent BUY to use
those same funds.

SELL RESERVATION
----------------
If an order needs 50 shares, reserve those shares so another concurrent SELL cannot also use them.

When an order is filled, cancelled, rejected or otherwise closed, reservations must be released
or consumed correctly.

This is a financial consistency requirement.


====================================================================
26. CONCURRENCY / RACE CONDITIONS
====================================================================

The system must safely handle concurrent requests.

Example failure to prevent:
User has ₹10,000.
Two requests arrive at the same time.
Each tries to buy ₹8,000.

A naive implementation could allow both and produce an impossible negative or overcommitted
balance.

TradeCore must use appropriate transaction boundaries, locking/atomic operations and database
constraints so financial state remains correct.

Do not claim concurrency protection merely because a method is marked transactional; reason about
actual race conditions and what data is being locked/updated.


====================================================================
27. IDEMPOTENCY
====================================================================

A mobile/browser request can time out even though the backend has successfully created an order.
If the client retries, the system must not create a duplicate financial operation.

Support idempotency for important mutating operations, especially order creation.

Conceptual behavior:
Same idempotency key + same relevant request
    -> return/reuse the original result

Same key + materially different request
    -> reject as an idempotency conflict

Persist enough information to make this behavior reliable.


====================================================================
28. RISK MANAGEMENT
====================================================================

Risk checks happen before execution.

Possible rules:
- maximum order amount
- maximum order quantity
- daily trading value limit
- maximum portfolio exposure
- account-level restrictions
- instrument-level restrictions
- configurable trading restrictions

Risk limits should be data/configuration driven where practical.

A risk rejection must explain the business reason to the user and should be auditable.


====================================================================
29. EXECUTION SIMULATOR
====================================================================

The execution engine is an internal simulation engine.
It must NOT place real trades with the market provider.

MARKET ORDER
------------
If bid/ask is available:
- BUY should prefer the current ask.
- SELL should prefer the current bid.

If bid/ask is unavailable:
- use the latest valid LTP/current quote according to the simulator's defined fallback rule.

Do not simply use a 5-second-old screen price if a newer valid market state exists.

LIMIT ORDER
-----------
A BUY LIMIT order becomes execution-eligible when the market state satisfies the BUY limit
condition.
A SELL LIMIT order becomes execution-eligible when the market state satisfies the SELL limit
condition.

PARTIAL FILLS
-------------
One order can produce multiple executions.

Example:
BUY 100 shares
Execution 1: 40 @ ₹1420
Execution 2: 35 @ ₹1422
Execution 3: 25 @ ₹1423

The order becomes FILLED only after the full requested quantity has executed.

The simulator should have an explicit and explainable partial-fill/liquidity rule.
Do not use arbitrary random numbers without recording/explaining why a fill occurred.

EXECUTION RECORD
----------------
Persist:
- execution ID
- order ID
- instrument
- side
- trading mode
- executed quantity
- execution price
- execution timestamp
- relevant market reference (where available)
- fees if implemented
- simulator/reference metadata needed for audit/reconstruction


====================================================================
30. POSITION MANAGEMENT
====================================================================

A position represents the user's holding/exposure in an instrument and must preserve the
relevant trading-mode/product semantics.

Conceptual fields:
- account
- instrument
- product/trading mode
- quantity
- reserved quantity
- average price
- realized P&L
- current/reference price
- updated timestamp

AVERAGE PRICE
-------------
Average price must be based on actual executed quantities/prices, not on order request price.

REALIZED P&L
------------
P&L resulting from quantity that has been closed/sold.

UNREALIZED P&L
--------------
P&L on currently open quantity using the latest valid market price.

Do not mix realized and unrealized P&L.


====================================================================
31. PORTFOLIO
====================================================================

Portfolio is the user's combined view of positions and valuation.

Should provide:
- invested value
- current value
- total P&L
- realized P&L
- unrealized P&L
- today's P&L where meaningful
- positions
- exposure information

During market hours, unrealized valuation uses the latest valid market quote.
After market close, the end-of-day valuation can use the valid closing market price.


====================================================================
32. LEDGER
====================================================================

Do NOT maintain only a mutable balance.

Every important financial movement needs a ledger record.

Possible ledger event/types:
- INITIAL_DEPOSIT
- TRADE_DEBIT
- TRADE_CREDIT
- FEE
- REVERSAL
- ADJUSTMENT
- OTHER controlled virtual-financial events where justified

Example:
INITIAL_DEPOSIT  +₹1,00,000
BUY_SETTLEMENT   -₹20,000
FEE                 -₹50
SELL_PROCEEDS      +₹5,000

Ledger records should be append-oriented and auditable.
Corrections should use compensating/reversal entries rather than silently rewriting history.


====================================================================
33. TRADING FEES
====================================================================

Fees are optional in the earliest core implementation but the design should support them cleanly.

If implemented:
- fee calculation must be deterministic/configurable
- fee must be recorded in the ledger
- order/execution totals must remain mathematically consistent

Do not add fake complex taxes/charges unless there is a clear business reason and the rules are
understood.


====================================================================
34. SETTLEMENT-LIKE PROCESSING
====================================================================

The core simulation can perform immediate or simplified settlement-like bookkeeping as long as
it remains internally consistent.

Do NOT pretend this is actual stock-exchange settlement.

If a settlement state is modeled later:
Execution
 -> settlement processing
 -> ledger/balance update
 -> position finalization

The basic order/execution/position/ledger flow must work correctly before additional settlement
complexity is introduced.


====================================================================
35. MARKET-DATA FAILURE HANDLING
====================================================================

External market data can fail.

EXPECTED BEHAVIOR
-----------------
Provider working:
    Data status = LIVE

Provider temporarily stops:
    retain last known valid market state
    record last update time
    mark data STALE

Longer failure:
    mark data UNAVAILABLE

When data returns:
    validate/normalize new data
    update internal market state
    mark data LIVE
    resume realtime distribution

CRITICAL SAFETY RULE
--------------------
Market-data failure must NOT corrupt:
- balances
- reservations
- orders/history
- executions already recorded
- positions
- ledger
- audit trail

If current market information is required to safely execute an order and the data is stale or
unavailable, the order should be rejected or kept from execution according to the defined order
policy. Do not execute using clearly unreliable data.


====================================================================
36. REALTIME FRONTEND EVENTS
====================================================================

WebSocket should distribute only relevant changes.

Potential event categories:
- MARKET_QUOTE_UPDATE
- MARKET_STATUS_UPDATE
- ORDER_UPDATE
- EXECUTION_UPDATE
- POSITION_UPDATE
- PORTFOLIO_UPDATE
- NOTIFICATION

Do not broadcast every event to every user if the user is not entitled or does not need it.
Market updates can be scoped to the instruments being watched/subscribed to.
User-specific financial updates must be authenticated and scoped to that user.

The frontend should reconnect automatically after temporary WebSocket disconnection.
Use sensible backoff and restore the subscription state.

The UI should never break permanently because the WebSocket briefly disconnects.

37. ORDER + EXECUTION + PORTFOLIO EVENT FLOW

Order accepted

    -> portfolio valuation updated
    -> notification generated
    -> audit record created

The final implementation does NOT require Kafka.
In-process/domain events plus reliable transactional handling are acceptable for a modular
monolith.

Do not use asynchronous processing in a way that can leave balance, position and ledger in an
inconsistent state. Financial state transitions must have a reliable consistency strategy.

43. DATABASE DESIGN PRINCIPLES
====================================================================

PostgreSQL is the primary transactional source of truth.

Use:
- foreign keys
- unique constraints
- check constraints where helpful
- indexes based on real queries
- proper numeric types for financial values
- UTC timestamps internally where practical, with IST/market timezone conversion for display
- explicit status/type fields
- optimistic versioning or locking strategies where required
- transactional operations for financial state changes

Do not use floating-point primitives for money where exact decimal behavior is required.
Use a precise database/application representation appropriate for currency and prices.

The database must preserve history rather than silently overwriting important financial events.


====================================================================
44. REDIS DESIGN
====================================================================

Redis is NOT the financial source of truth.

Good Redis use cases:
- latest quote/current market state
- hot instrument data
- short-lived idempotency coordination where appropriate
- rate limiting
- temporary WebSocket/subscription coordination
- frequently read non-financial data

Do not put the only copy of a user's financial balance, ledger or execution history in Redis.

If the Redis cache disappears, PostgreSQL must remain authoritative and the application should be
able to rebuild/reload required hot state.


====================================================================
45. MARKET DATA INTERNAL LAYERS
====================================================================

Recommended conceptual separation:

A. PROVIDER ADAPTER
   Talks to the current NSE MCP source and knows provider-specific formats.

B. NORMALIZER / VALIDATOR
   Converts provider data into TradeCore's internal format and rejects malformed values.

C. MARKET ENGINE
   Maintains the latest valid market state, freshness and market/session interpretation.

D. HISTORICAL AGGREGATOR
   Produces/updates candles and retention-aware history.

E. DISTRIBUTION
   Publishes relevant changes to backend consumers and WebSocket clients.

F. EXECUTION INPUT
   Supplies a consistent latest-valid quote to the simulator.

The order engine should depend on internal market interfaces/data, not directly on NSE MCP.

- mass assignment of protected financial fields
- exposure of provider secrets
- insecure debug endpoints in production-like configuration


====================================================================
55. BUSINESS CONSISTENCY RULES
====================================================================

Important invariants:

1. A FILLED order cannot later become PENDING/CANCELLED.
2. An executed quantity cannot exceed requested order quantity.
3. Order executed quantity + remaining quantity must remain mathematically consistent.
4. Reserved funds cannot exceed available/eligible account funds.
5. Reserved sell quantity cannot exceed available sellable position quantity.
6. Ledger entries must correspond to valid financial events.
7. Position quantity cannot become negative under the supported trading model.
8. Realized P&L must be based on actual closed quantities and execution prices.
9. Unrealized P&L must use a valid current/reference market price.
10. Duplicate requests must not create duplicate financial effects.
11. Every important order status change must be explainable through order events/audit data.
12. External market-data failure must not rewrite or corrupt financial truth.
13. Redis loss must not destroy permanent financial history.
14. Provider-specific fields must not leak into core domain assumptions.

68. AI CODING AGENT + TERMINAL DEVELOPMENT WORKFLOW
====================================================================

This project is intended to be developed by an AI coding agent working DIRECTLY inside the
existing TradeCore repository from the terminal/IDE environment.

The agent is NOT expected to generate a new ZIP project for every change.

The working model is:

    Existing TradeCore repository
            |
            v
    AI coding agent in terminal
            |
            +--> inspect current files
            +--> inspect current tests/build state
            +--> implement one scoped task
            +--> run validation
            +--> review changes
            |
            v
    Same TradeCore repository continues to the next task

The same project directory is the source of implementation truth. The specification is the
source of product/behavior truth.

68.1 FIRST-RUN DISCOVERY
------------------------
Before making code changes, the agent MUST:

1. Read this complete specification.
2. Inspect the repository tree.
3. Inspect existing backend/frontend build files and configuration.
4. Inspect existing tests.
5. Inspect database/migration files and current schema strategy.
6. Inspect the current Git status.
7. Identify the current implementation phase.
8. Identify existing working features that must not be broken.
9. Check whether the requested feature already exists before creating new classes/modules.
10. Record any existing build/test failures before changing them.

The agent MUST continue from the existing project rather than regenerate the project from scratch.

68.2 DIRECT REPOSITORY WORK
---------------------------
The agent MUST:

- work inside the current TradeCore project directory
- edit the actual project files
- preserve existing working code
- create new files only when the feature actually requires them
- keep package/module structure consistent with the current project
- use the existing build system and dependency management
- reuse existing utilities/components when appropriate
- inspect neighboring code before introducing new patterns

The agent MUST NOT:

- generate a new ZIP after each task
- replace the whole repository with a newly generated project
- copy the same classes into alternate packages
- create parallel versions of the same service/controller/repository
- delete working code merely because another implementation style is preferred
- move large parts of the project without a concrete reason
- introduce unrelated refactoring during feature work

ZIP/export generation is allowed only when the user explicitly asks for an archive.

68.3 TASK-SCOPED IMPLEMENTATION
-------------------------------
The agent MUST work on ONE major scoped task at a time.

For every task:

1. Understand the requested behavior.
2. Find the existing code relevant to the behavior.
3. Identify dependencies and affected modules.
4. State a short implementation plan.
5. Make the smallest cohesive set of changes that satisfies the task.
6. Run targeted tests/build checks.
7. Fix failures caused by the implementation.
8. Review the resulting diff and check for unintended changes.
9. Report what changed and what was verified.
10. Stop at the task boundary unless the user asks for the next task.

Do not combine unrelated features simply because they can be coded together.

68.4 PLAN BEFORE LARGE CHANGES
------------------------------
For architectural, financial, database, security or cross-module changes, the agent should plan
before editing.

The plan should identify:
- affected modules
- affected entities/tables
- API changes
- transaction boundaries
- concurrency implications
- security/authorization implications
- test cases
- migration implications
- realtime/event implications

Do not write a large amount of code before understanding these dependencies.

68.5 VALIDATION LOOP
--------------------
After a logical implementation change, the agent MUST validate it.

Preferred loop:

    Inspect
      ->
    Plan
      ->
    Implement
      ->
    Compile/build
      ->
    Run focused tests
      ->
    Run broader tests where appropriate
      ->
    Inspect changed files
      ->
    Continue

A green frontend screen is not sufficient proof that a financial workflow is correct.

For financial features, verify:
- database state
- transaction behavior
- invariants
- status transitions
- ledger effects
- position effects
- duplicate-request behavior
- concurrent-request behavior

If validation fails, fix the root cause before starting another unrelated feature.

68.6 NEVER HIDE FAILURES
------------------------
The agent MUST NOT:

- delete failing tests to make the build green
- weaken assertions merely to pass tests
- disable validation because it is inconvenient
- swallow exceptions without a justified business reason
- silently replace a real provider failure with fake market data
- claim success when build/tests have not been run
- ignore a known consistency problem because the UI appears correct

Existing failures that predate the current task should be reported separately from failures introduced
by the current task.

68.7 GIT / CHANGE SAFETY
------------------------
Use Git as the change-safety mechanism.

The agent should:
- inspect Git status before major work
- keep changes reviewable
- avoid destructive Git commands
- never silently reset/discard the user's work
- never force-push or publish changes unless explicitly asked
- suggest a commit point after a meaningful validated milestone

Before a large risky change, the agent should identify what can be safely reverted.

68.8 DATABASE / MIGRATION SAFETY
-------------------------------
Database changes are high-risk.

The agent MUST:
- inspect existing schema/migration history before changing it
- prefer forward migrations
- avoid rewriting old migrations that may already have been applied
- preserve foreign keys and important constraints
- consider concurrent requests against the affected rows
- never casually drop production-like financial tables/columns
- verify that application models and database schema agree

If a destructive migration is unavoidable for the requested scope, it must be clearly identified before
execution and not hidden inside an unrelated change.

68.9 DEPENDENCY SAFETY
----------------------
Before adding a library:
- check whether the project already has a suitable dependency
- confirm that the library solves a real requirement
- keep the dependency set understandable
- avoid adding multiple libraries for the same job

Do not upgrade unrelated dependencies merely because newer versions exist.
Do not change framework versions during ordinary feature implementation unless version compatibility
requires it.

68.10 FINANCIAL CODE SAFETY
---------------------------
Financial code receives stricter treatment than normal CRUD code.

Before modifying order, balance, reservation, execution, position, P&L or ledger logic, the agent
MUST review the relevant business invariants in this specification.

Every financial change should consider:
- exact decimal arithmetic
- transaction boundary
- row/version locking or equivalent concurrency control
- idempotency
- duplicate event/request behavior
- failure/rollback behavior
- order-state legality
- balance/position/ledger consistency
- auditability

Never update a user's balance as an isolated mutable field change without considering the corresponding
financial history and consistency model.

68.11 MARKET-DATA INTEGRATION SAFETY
------------------------------------
The current market-data provider is NSE MCP.

The agent MUST keep provider-specific logic inside the market-data integration boundary.

The core order/risk/position/ledger/portfolio logic MUST consume TradeCore's internal normalized market
model rather than directly depending on NSE MCP payload classes or provider-specific assumptions.

The agent MUST:
- inspect the actual provider interface available to the project
- use only supported fields/capabilities
- keep credentials and tokens backend-side
- validate and normalize incoming data
- track data freshness
- handle provider disconnect/reconnect
- prevent stale/unavailable data from being mistaken for LIVE data
- avoid fake/random prices in the normal live product flow

If the provider cannot supply a requested feature directly, do not invent a capability. Use an explicit
supported fallback, existing stored data, or clearly mark the capability as unavailable.

68.12 FRONTEND/BACKEND BOUNDARY
-------------------------------
Next.js is the product UI.
Spring Boot is the business authority.

The frontend MUST NOT be the authority for:
- account balance
- order validity
- risk decisions
- position quantity
- execution state
- ledger truth

The backend MUST enforce authorization even when the frontend already hides a screen or route.

The frontend should request only the data required by the screen and should not call the external market
provider directly.

68.13 REALTIME DEVELOPMENT RULE
-------------------------------
Do not create independent one-second polling loops for each stock or widget.

Use the existing backend market-data flow and authenticated WebSocket distribution strategy.

Realtime UI updates must:
- update only affected UI state where practical
- avoid full-page refreshes
- avoid duplicate subscriptions
- reconnect safely after temporary disconnects
- preserve user-specific event isolation

68.14 CODE QUALITY / MAINTAINABILITY

Prefer:

- explicit business rules
- understandable control flow
- meaningful validation
- useful error codes
- testable services

Avoid:

- unnecessary generic frameworks inside the project
- deep inheritance hierarchies
- duplicate business rules

70. PERFORMANCE "NOT SLOW" QUALITY BAR
====================================================================

The AI must proactively look for:
- unnecessary API round trips
- duplicate API calls
- large initial JavaScript bundles
- chart libraries loaded on every page
- full page rerenders caused by quote updates

- unbounded history queries

- synchronous network calls inside database transactions
- repeated market-provider calls from multiple components
- WebSocket message storms
- large JSON payloads when a compact projection would work

When a performance issue is found, prefer a simple measurable fix.

Examples:
- cache stable data
- send compact DTOs
- paginate
- use projections
- lazy-load charts
- batch updates
- use Redis for hot state
- use WebSocket for live updates
- index common queries
- keep transaction scope small
